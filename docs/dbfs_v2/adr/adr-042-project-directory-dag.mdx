## Context

DBFS v2 is a **per-file** DAG. It answers "what is this UUID at revision R"
and, by itself, has no object that means "this project": which identities
exist, at which paths, bound to which content. Snapshots, fork, whole-tree
merge, provenance, and the explorer all need that object.

A first design named a project state as a derived fold `(S, B)` — a clock cut
`S` through `file_events` plus per-file branch heads, with a stored manifest
only when something named a snapshot. That is not how the store works. The
authoritative project is a **stored DAG of hashed nodes**. The clock still
ticks (revisions, path-op notifications, branch births, reflog, the branch
rail); it does not name the tree.

Four facts a project node must pin, and where they live now:

| fact | where it lives |
|---|---|
| identity | `file_nodes.id` (UUID). `file_nodes.path` is a unique slot (`/.nodes/<id>`), not the user-visible location. |
| location | merkle directory entries on a project node (`path` is reconstructed by walking names). |
| content, running | the live per-file line `(file_node, project_branch)` — a submodule pointer at a branch, not a rev. |
| content, snapshot | `revision_id` stamped on file entries of that snapshot tree. |

Existence is presence on the running head. Delete does not destroy the UUID or
its content DAG. Restore / recreate walk parent project nodes for the last
path → UUID.

## Decision

**The project is a stored DAG. Every public path op appends one hashed running
node and moves HEAD onto it. Content writes do not. There is no dirty working
tree — this is the authoritative backing store.**

### Identity

A `FileNode` is identity: UUID, POSIX, symlink target, binary flag, the
per-file revision DAG. The user-visible path is **location**, held by the
project tree, not by the node row.

On the wire (PROTOCOL 12) a document is `(project, file_node_id, branch)`.
Tabs keep one Monaco per that triple; the tab **label** follows a rename; the
path field is a location cache. The explorer takes `fs/tree` as a snapshot
(connect, branch switch, import, merge, bulk `created` at `/`) and otherwise
applies `created` / `renamed` / `deleted` in place.

### Two graphs

```d2
direction: right

identity: "identity DAG\n(FileNode UUID)" {
  direction: down
  r1: "rev"
  r2: "rev"
  r3: "rev"
  r1 -> r2 -> r3
}

project: "project DAG\n(path op → node)" {
  direction: down
  n1: "running"
  n2: "running"
  snap: "snapshot"
  n3: "running"
  n1 -> n2 -> n3
  n2 -> snap: "parent\n(HEAD does not move)"
}

bind: "binding" {
  running: "running: live line\n(file_node, project_branch)"
  frozen: "snapshot: revision_id\non file entries"
}

identity -> bind
project -> bind
```

- **Identity DAG.** Edits on a minted UUID. Keystrokes, blob writes, per-file
  branch, per-file merge. Unchanged by a path op except that the project node
  still points at the same UUID.
- **Project DAG.** Create / rename / delete / restore / adopt. `mkdir -p` plus
  `create_file('/a/b/c')` is **one** public path op → one running node. Linear
  on a branch (parent = previous running node); a merge node has a second
  parent. Fork hangs the child's first running node off the parent's then-head.

`Store#state(branch:, seq:)` is `ProjectDag.view` of that branch at clock `S`
(omit `seq:` for HEAD): the running node with `seq ≤ S`, each file's
identity-rev from that line's `branch_heads` reflog (`seq ≤ S`). Live HEAD
uses the line's current head. It is not `ProjectState.at(seq:)` / `(S, B)` —
one branch, not a BranchSet fold. `BranchSet`, `merge_project`, and the old
`project_snapshots` table are gone.

### Running head

A running node's files point at a **live content line**, the way git would if a
submodule recorded a branch instead of a commit. `content_branch_id` is not
stored on the tree (see Merkle). Resolution is
`(file_node_id, project_branch_id)` (unscoped, so a tombstoned project branch
still names its lines). A content write advances that line and **does not**
append a project node.

HEAD is a pointer at the latest **running** node (`project_branches.head_node_id`).
The tip always advances on a path change. There is no dirty WT relative to
HEAD; the store *is* HEAD.

### Snapshots

Snapshots are rows in the same `project_nodes` table (`kind: snapshot`).
`snapshot!(name)` freezes each file's identity-rev onto the tree and hangs the
new node off the running head as `parent`. **HEAD does not move onto the
snapshot.** Unnamed snapshots (`freeze!`) are the fork/merge-base cut: later
writes on those content lines cannot move the recorded tree.

Squash / compact of running history is out of scope. A snapshot is the bound
for "what was frozen"; history reads of path ops walk parent running nodes
(and, for a delta from a named cut, start at that snapshot). There is no
storage sweeper that folds running nodes away.

### Merkle directories

A directory is a content-addressed object:

- `project_trees.id` = SHA-256 of the sorted children
  (`name`, `file_node_id`, `ftype`, `child_tree_id`, `revision_id`).
- `project_tree_entries` are **basenames**. Folders carry `child_tree_id`;
  snapshot files carry `revision_id`. No `content_branch_id` — forks could not
  share trees if the line id lived on the entry.
- A project node is `kind`, parents, optional `name`, `root_tree_id`,
  `project_branch_id`, and `seq` (the clock at insert). Its id is SHA-256 of
  kind/parents/name/root/**branch** — **seq is out of the hash**. Trees still
  share across branches; running nodes do not. Two writers of the same tree
  on the same branch still hash-cons; `S` names when this row was born.

A path op copy-on-writes only the **dirty spine** (changed leaf + ancestor
dirs). Unchanged sibling directories keep their tree id. A folder move/delete
reuses the child's tree pointer; descendants are not rewritten.

```d2
direction: down

root: "root tree" {
  a: "wide/  → T_wide"
  b: "README → file UUID"
}

wide: "T_wide" {
  f0: "f0.txt"
  f1: "f1.txt"
  fN: "…"
}

root -> wide
note: "add /wide/new.txt\n→ new T_wide' and new root'\nT_wide remains; README's entry is copied into root'"
```

Fork shares the parent's running `root_tree_id`. The requirement is that the
child does not follow later parent edits. This implementation mints a new
per-file `Branch` at the parent's then-head (eager, O(files)). Lazy lines —
absent until first write, content read from the freeze — also satisfy that;
eager minting is not the requirement.

A freeze **walk** is O(files): it must read every live line to stamp
`revision_id`. The first freeze cannot share directory objects with the
running tree (running entries have `revision_id` nil; snapshot entries do
not). After that, `put_tree!` reuses any directory whose stamped children
already exist. O(N) is the walk, not the storage.

A full-flat copy of every path onto every running node is rejected: `cp` of 5
files in a 10k-file project must not insert ~50k rows.

### Clock and events

Every project has one monotonic counter (`Clock.tick!` inside the writing
transaction, so seq order is commit order). It stamps:

- each revision
- each **project-DAG insert** (`project_nodes.seq`; one tick per running or
  snapshot node)
- each path-op **notification** (`file_events`: `created` / `renamed` /
  `deleted` / `restored`; **the node's seq**, N rows for a subtree — not a
  second tick)
- branch birth (`branches.seq`, `project_branches.seq`)
- every head move (`branch_heads` reflog — a fast-forward ticks even when no
  revision is created)
- `ProjectMergeRecord.seq`

`file_events` are **not** the tree. The explorer uses them; `ProjectGraph`
buckets them; restore/find_any walk **parent project nodes**, not the event
log. Recreating a path over a tombstone is a `created` on the same UUID.

`S` is a stamp across the two graphs so you can examine a branch at any point
between explicit snapshots, including keystrokes: path-op node (`seq ≤ S`) +
content-line heads (`branch_heads.seq ≤ S`). `Store#state(branch:, seq:)` is
that cut. Content writes do not append a project node; they only advance the
line and the clock.

Deleting a per-file or project branch is a tombstone. Revisions keep
`branch_id`. The name is free (partial unique index). Re-homing history onto
`main` is rejected — a past state would gain revisions that were never on
`main`.

### Project branches

`project_branches` rows have UUID identity. `main` is a row like any other for
the **path index**. A tip is `head_node_id`. `fork_node_id` / `base_node_id`
are frozen project nodes (the parent at fork; then, after each merge between
the pair, a freeze of the source).

`BranchFs` is the filesystem of one project branch, including main: find /
list / tree, create / delete / restore / move, `adopt!`, `ensure_content_branch!`.
`Store` operations take `branch:` and dispatch. A file created only on a
branch is a UUID whose location exists on that head and not on main's.

### Project merge

Three-way merge of the whole tree **by node identity**, reconcile-or-conflict,
atomic. Base is the child's `base_node` (else `fork_node`); ours is the
target's running head; theirs is the source's. Per node, the side that changed
wins (delete, move, `adopt!`, content take or per-file auto-merge). Both sides
changing differently is a conflict (`rename/rename`, `rename/delete`,
`modify/delete` and reverses, `add/collision`, `content`). Identity conflicts
take `ours` / `theirs` / `path`; content conflicts use the per-file three-way
merge. Any unresolved conflict rolls back. `dry_run: true` is the same
transaction, always rolled back.

After a successful merge the source's running head is frozen and becomes the
child's next `base_node`.

### Materialization

On-disk working area is the user's choice **per branch**, except `main`, which
is always the project root (`/srv/projects/<project-uuid>`). Any other branch
is DBFS-only until toggled on: then `<root>/.branches/<branch-uuid>` (uuid, so
a reused name never lands in a stale directory) with its own flusher/watcher
pair over a `BranchView`. `.branches` is pruned from main's loader and watcher.
Toggle-off stops the pair and removes the directory; the DAG keeps the branch.
Materialized branches come back on worker boot.

PROTOCOL 11: `fs/project_branch_materialize { name, on }` →
`fs/project_branch_materialized`; branches carry `disk`.

### ProjectGraph

The **Branches** tab is not the project DAG. `ProjectGraph` condenses seq-stamped
activity (edits, file events, fork, merge) into runs with a pause gap, one lane
per project branch, same rail layout as the per-file history pane. Stepping a
branch's trees over time (event text + tree at a project node, identity chips
for moves) is a different surface and is not built.

## Consequences

**Positive**

- A project revision is a stored, hashed node. Provenance is a node id; a
  named snapshot is a frozen tree hanging off a running head.
- Path ops pay for the dirty spine, not the whole project. Forks share running
  trees; they do not share running **nodes** (`project_branch_id` is in the
  node hash).
- Rename and delete are history: parent nodes still hold the old binding;
  HEAD does not. Recreate keeps the UUID.
- Main's path index is the same mechanism as every other project branch.
- Branch deletion does not alter the past.

**Negative / constraints**

- The clock row still serializes seq assignment. Writes are batches, not
  keystrokes; the lock is the stronger ordering ADR-041 already requires.
- Content writes take `FOR SHARE` on the **project branch** row. Path ops,
  snapshots, forks, and merges take `FOR UPDATE` on that same row. A freeze
  then waits for in-flight content commits; a content write waits for an
  in-flight freeze. Locking the per-file line alone does not close the
  snapshot race (freeze and a content write would never touch the same row).
- A freeze walk is O(files). The first freeze rewrites every directory
  (stamped `revision_id` vs running nil). Later freezes reuse unchanged
  subtrees via `put_tree!`. O(N) is the walk, not the storage. Running path
  ops must not be O(files).
- This implementation mints a line per file at fork. That is one way to keep
  the child from following the parent; lazy-from-freeze is another.
- `branch_entries` remains in the schema from the first index; it is not the
  tree. The live index is `head_node.root_tree_id`.
- `write_blob` still has no `MAX_BLOB_BYTES` guard (decisions #26). Ingest and
  the loader cap at `ProjectFs::MAX_FILE_SIZE` (5 MB).

### Merkle hash

```text
tree_id = SHA256( "tree\n" + sort_by name: name, file_node_id, ftype, child_tree_id, revision_id )
node_id = SHA256( kind, parent_id, second_parent_id, name, root_tree_id, project_branch_id )
# project_nodes.seq is stored on the row, not in node_id
```

Identical children in any insert order agree. `put_tree!` is content-addressed
and uses a savepoint so a concurrent insert of the same tree does not abort the
outer transaction (the same pattern as `ProjectDag.insert!`).

### Events (notifications)

```jsonc
// file_events — append-only; one seq per public path op
{ "seq": 6, "file_node_id": "…", "kind": "renamed", "path": "/c.rb", "from_path": "/b.rb" }
{ "seq": 9, "file_node_id": "…", "kind": "deleted",  "path": "/c.rb" }
{ "seq": 12, "file_node_id": "…", "kind": "restored", "path": "/c.rb" }
```

A folder move emits one `renamed` per descendant under one `seq`. The tree
change is one project node that relocates the folder's child tree.

## What exists

Server (`DbfsV2`):

- Clock, `file_events`, `branch_heads`; revisions and branches stamped with
  `seq`; tombstones; `ProjectGraph`.
- `project_nodes` (`kind` running|snapshot, parents, `root_tree_id`,
  `project_branch_id` in the hash, `seq` out of it),
  `project_trees` / `project_tree_entries`; `ProjectDag` (dirty-spine builder,
  `view(seq:)`, `node_at`, `lookup` / `flatten`, freeze/snapshot); `BranchFs`;
  `Store#state(branch:, seq:)`, `#snapshot!`. Path-op FileEvents reuse the
  node's seq. Content writes `FOR SHARE` the project branch row.
- `project_branches` (`head_node_id`, `fork_node_id`, `base_node_id`);
  `ProjectMerge.branches`; `adopt!`; `BranchView`.
- Identity slot `/.nodes/<uuid>`; PROTOCOL 12 document key.

Worker: PROTOCOL 10–12 as above; `BranchMirrors`; `OPEN_DOCUMENTS` keyed by
FileNode UUID; `fs/tree` and grep use the project-branch index for main too.

Client: workspace branch; explorer event-only patch; tabs keyed by
`(file_node_id, branch)`; project-merge tab; Branches rail (`fs/project_dag`).

## Open questions

1. **Checkout of a past project node** onto a watched directory (pause the
   watcher, write the tree, resume). Materializing a live branch already writes
   the directory before its watcher starts.
2. **On-disk names.** Requested and not built: `<root>/<branch-name>` →
   `.branches/<uuid>`. Today's layout is uuid-only under `.branches`.
3. **Agent file tools** scoped to the workspace project branch.
4. **A project-identity visualizer** (slider over running nodes, FileEvent
   captions, tree at that node with UUID chips so a move is a transition, not
   a create+delete). Distinct from `ProjectGraph`. `state(branch:, seq:)` is
   the read cut that slider would step.
5. A pending set-level merge still has no stored "merge in progress";
   resolutions travel with the next attempt.

## Out of scope

- **Compact / squash of running project nodes.** Snapshots freeze; they do not
  license a sweeper.
- **Running a merge or transform outside the server lock.** Offline editing
  changes ADR-041 first.
- **Agent-conversation DAGs** (ADR-032).

## Alternatives considered

- **`(S, B)` as the project revision** (`ProjectState.at`, `BranchSet`,
  snapshot = materialized fold, `merge_project`). Rejected: that is a derived
  frontier, not a stored path DAG. Tip mutation plus a fold cannot name how
  the tree got from A to B to C. Removed.
- **Mutated `branch_entries` as the only live index.** Rejected as the project
  revision (same reason). `main` using `file_nodes.path` while other branches
  used an index was also rejected: main is a `ProjectBranch` like any other.
- **Full-flat `project_node_entries` per node.** Built first, then rejected:
  every path op copied the whole tree. Merkle dirty-spine replaces it.
- **Delta nodes from the last snapshot, with a compact sweeper.** Rejected the
  sweeper. History reads are cheap from the last **explicit snapshot** without
  compacting running nodes. Merkle was chosen for write amplification.
- **`content_branch_id` on every tree entry.** Rejected: a fork would rewrite
  every directory (or the child would inherit the parent's line ids). Running
  content is resolved by project-branch membership so trees can be shared.
- **Overlay that reads through to `main` for untouched files.** Rejected: the
  child would move when `main` did. Fork freezes the cut so the child does
  not follow later parent edits. Eager per-file lines at fork are one
  implementation of that; lazy lines that read the freeze until first write
  are another.
- **HEAD moves onto a snapshot.** Rejected: a snapshot hangs off the running
  head; content writes must keep landing on the live lines.
- **Branch names as identity.** Rejected: reuse would attach old history. UUIDs
  for `FileNode`, `ProjectBranch`, and per-file `Branch` rows; names are labels.
- **A timestamp as the cut.** Rejected: per-file writes are independent
  transactions. The clock is commit-ordered; project nodes are hashed.
- **A Postgres `SEQUENCE` for `seq`.** Rejected: not commit-ordered.
- **Re-homing a deleted branch's revisions to `main`.** Rejected: it changes
  the past.
